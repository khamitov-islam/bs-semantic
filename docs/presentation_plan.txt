1. ЗАДАЧА И ОГРАНИЧЕНИЯ   (2 мин)
══════════════════════════════════════════════════════════════════

Заказ: on-premise семантический поиск / RAG по официальной справке
Business Studio. Ответ на каверзные вопросы по функционалу + ссылка
на файл справки. Никакого облака.

Корпус: DokuWiki + плагины вендора.
653 страницы DokuWiki, ~3 млн символов. 
Наивная очистка убила бы самое ценное для блиц-теста:
пути по меню в {{bslink>...|GUID}},
подписи таблиц <startTableBox>,
картинки с подписями, 
объединение строк ::: в таблице горячих клавиш. 
Поэтому свой конвертер — единственный «велосипед»; остальное на LangChain / Qdrant / Ollama / Streamlit.
После очистки: 573 страницы, ~2.5 млн символов.
Полный дамп в git не кладём (проприетарный контент).
В репозитории — 25 страниц выборки.

Гипотеза на старте: качество упрётся не в «какую LLM взять»,
а в разбор разметки и в то, как нарезать таблицы и меню.

2. АРХИТЕКТУРА ОДНИМ ВЗГЛЯДОМ   (1 мин)
══════════════════════════════════════════════════════════════════

  DokuWiki .txt
      → свой парсер (bslink, TableBox, :::, BOM, подписи рисунков)
      → чанки (header-aware + recursive, LangChain)
      → Qdrant embedded: dense + BM25
      → вопрос
      → hybrid RRF  [+ вторая коллекция строк таблиц]
      → реранкер bge-reranker-v2-m3 fp16
      → Ollama Qwen3 8B
      → ответ с [1][2] и путём к файлу

Свой код — парсер и склейка. Остальное — готовые библиотеки.
Qdrant не потому что «SOTA-индекс»: на 2500 чанках ANN не важен.
Нужны dense+BM25 и RRF в одном процессе без сервера.


══════════════════════════════════════════════════════════════════
3. ЭТАП 0. ПАРСЕР   (3 мин)   — самое сильное место рассказа
══════════════════════════════════════════════════════════════════

Идея. Готовый dokuwiki→md не понимает плагины Business Studio.

Гипотеза. Если выкинуть разметку «как HTML», пропадёт ровно то,
по чему пользователь ищет: путь меню, клавиша, подпись таблицы.

Эвристики / ловушки корпуса:
  • {{bslink>Главное меню → …|GUID}}
        видимый текст — путь, после «|» — GUID. Наивная очистка
        выкидывает меню.
  • <startTableBox>…<endTableBox|Таблица 1. …>
        подпись ПОСЛЕ таблицы, при нарезке отрывается.
  • ::: в таблице горячих клавиш
        объединение строк. Без наследования Ctrl+R остаётся
        только у первой строки. Вопрос «какой клавишей Права
        доступа?» становится неотвечаемым.
  • [{{ path|Рисунок 1. … }}] — эмбеддеру нужна подпись, не файл.
  • BOM у 51 страницы прятал H1.
  • оглавления из одних ссылок, iframe, contextnavigator — выкинули.

Метрика этого этапа: не nDCG, а тесты на реальных конструкциях
(24 теста парсера) + инспектор корпуса в UI (слева сырой DokuWiki,
справа то, что уходит в индекс).

Что сказать, если спросят «почему не pandoc / mwlib»:
  потому что плагины вендорские. Это единственный слой, который
  нельзя купить готовым.


══════════════════════════════════════════════════════════════════
4. ЭТАП A. ЧАНКИНГ   (3 мин)
══════════════════════════════════════════════════════════════════

Идея. Резать по оглавлению справки - заголовку, не «каждые N символов».
LangChain: MarkdownHeaderTextSplitter + RecursiveCharacterTextSplitter.
Бюджет токенов минус шапка (заголовок раздела).
Шапка разорванной таблицы возвращается второму фрагменту.

Гипотеза 1. 256 токенов лучше 512 на каверзных вопросах.
Гипотеза 2. Оверлап 15% лучше 0% и 30%.
Гипотеза 3. Parent-document, rows(строки в таблицах), no breadcrumbs даст плюс.

Протокол. Сетка 256/384/512 × 0/15/30% на e5-base, БЕЗ реранкера
(реранкер сглаживает разницу). Потом абляции на лучшей клетке.

Метрика: page-level nDCG@10 / Hit@k (ranx). Оценка по странице,
чтобы сравнивать нарезки разной длины.

Результат сетки:
  256/15% чуть лучше на ручных (manual nDCG 0.60).
  512/15% тот же общий nDCG при вдвое меньшем индексе.
  Решение: 512/15% — не жадничать по nDCG на 0.01 ценой индекса.

Абляции. В первом прогоне parent / rows / no breadcrumbs дали
После изоляции коллекций:
  fixed            0.709   заголовки нужны
  parent-document  0.716   тот же embed-текст, меняется только LLM-контекст
  rows             0.731   лучше, но это другой корпус
  no breadcrumbs   0.731   крошки на e5-base мешают

Эвристика, которую оставили: заголовки раздела в чанке нужны;
полный путь «Руководство пользователя / …» в эмбеддере — нет
(на USER-bge-m3 manual nDCG 0.75 → 0.77).


Честно сказать: первую цифру по абляциям мы сами испортили
и пересчитали. Это плюс, не минус.

5. ЭТАП B. ЭМБЕДДИНГИ   (2 мин)
══════════════════════════════════════════════════════════════════

Идея. Сравнивать модели на фиксированной нарезке 512/15%, без реранкера.

Кандидаты: e5-small/base/large, BERTA, ru-en-RoSBERTa,
USER-bge-m3, «ванильный» bge-m3.

Гипотеза. Русскоязычный USER-bge-m3 лучше e5-large и лучше
универсального bge-m3 на этой справке.

Результат (без реранкера):
  USER-bge-m3   nDCG 0.78   Hit@3 0.89
  e5-large      0.74 / 0.83
  bge-m3        ниже USER

Префиксы query/passage для e5 и RoSBERTa обязательны —
без них качество падает. У USER-bge-m3 префиксы пустые.

Почему не сменили движок индекса: на 2500 векторах поиск полный.
SOTA-эмбеддер ещё может дать ~0.02–0.04 nDCG (как e5→USER),
но это лотерея и полный пересчёт индекса, не порядок.


══════════════════════════════════════════════════════════════════
6. ЭТАП C. СХЕМА ПОИСКА   (3 мин)
══════════════════════════════════════════════════════════════════

Идея. Dense + BM25 в одной коллекции, RRF из коробки, затем
кросс-энкодер на 16 кандидатах.

Гипотеза 1. Hybrid лучше dense и лучше BM25.
Гипотеза 2. Реранкер даст основной скачок Hit@3.
Гипотеза 3. 32 кандидата лучше 16.
Гипотеза 4. Свои веса RRF «короткий запрос → BM25» лучше равного RRF.

На e5-large:
  dense                Hit@1 0.54   Hit@3 0.75   nDCG 0.65
  dense + реранкер     Hit@1 0.67   Hit@3 0.92   nDCG 0.77
  hybrid + реранкер    Hit@1 0.71   Hit@3 0.88   nDCG 0.76
  BM25 один слаб (Hit@1 0.33)

Реранкер — главный рычаг качества поиска и главный рычаг
задержки поиска (~2 с тёплый, ~6 с холодный).

Отвергнуто:
  32 кандидата     Hit@3 +0.015, nDCG −0.013, 4.6 с
  взвешенный RRF   nDCG 0.80 → 0.78, Hit@1 0.72 → 0.69
                   Qdrant hybrid оказался лучше нашей эвристики.
                   На 24 ручных весах не учили — переобучение.

Эвристика, которая выжила: лексическое раскрытие запроса БЕЗ LLM
(«клавиш» → «горячая клавиша»). +0.002 nDCG, +0–50 мс.


══════════════════════════════════════════════════════════════════
7. ЭТАП ТАБЛИЦ   (2 мин)   — последнее содержательное улучшение
══════════════════════════════════════════════════════════════════

Идея. Header-aware режет таблицу посередине. Даже с возвратом шапки
BM25 ищет «Ctrl+R» внутри куска на 400 токенов соседних строк.

Гипотеза. Отдельная коллекция СТРОК таблиц даст больше, чем
ещё одна эмбеддинг-модель.

Проверили честно на USER-bge-m3 512 (раньше rows был только
на e5-base 256 — однофакторный план):
  весь корпус в rows     nDCG 0.813   Hit@3 0.875   Hit@1 0.72
  dual-index (проза markdown + строки таблиц)
                         nDCG 0.819   Hit@3 0.875   Hit@1 0.75

Dual-index включён. Прозу в rows не переводим: длинные разделы
(ветки, BPMN) в формате «Колонка: значение» хуже.

Цена: +~2700 коротких чанков, +100 мс поиска, бейслайн цел.


══════════════════════════════════════════════════════════════════
8. ЭТАП D. LLM   (2 мин)
══════════════════════════════════════════════════════════════════

Идея. Ответ только по фрагментам, цитаты [1][2], отказ если нет
в справке. think: false — «размышления» Qwen3 на RAG не нужны.

Сравнивали: Qwen3 8B, Gemma3 12B QAT, Vikhr-Nemo 12B
(у Vikhr свой Modelfile: шаблон llama3 без лишних спецтокенов).

Протокол: 12 ручных + 6 ловушек, локальный LLM-судья
(обоснованность / полнота), корректность ссылок, trap refusal.

Результат:
  Qwen3   ~24 с   citation 1.0   trap 1.0   faithfulness ~0.96
  Gemma   медленнее, полнота выше, иногда отвечает вне справки
  Vikhr   cited_gold слабее

Выбрали Qwen3: отказы важнее полноты в справке вендора.

Прогрев: холодный поиск 6.1 с → 2.2 с. Генерация 24 с не лечится
прогревом — это инференс 8B, не загрузка весов.


══════════════════════════════════════════════════════════════════
9. ОЦЕНКА И ЧЕСТНОСТЬ МЕТРИК   (1.5 мин)
══════════════════════════════════════════════════════════════════

Золотой набор:
  76 ручных (было 24). Писали по страницам, не генератором из чанка.
  12 ловушек (Telegram, цена, 2FA, нейросеть, релиз 7, Kafka,
              Slack, iOS, Keycloak, цена Portal, Camunda, Kubernetes)
  40 синтетических из чанков — отдельно, они завышают nDCG.

Считаем page-level nDCG/Hit, не chunk-level: иначе нарезки
несравнимы.

Почему 24 было мало. Hit@1 — доля. При p=0.75 стандартная ошибка
sqrt(p(1-p)/n): на 24 вопросах ±9 п.п. (один вопрос = 4 пункта),
на 76 — ±5 п.п. (один вопрос = 1.3 пункта). Переход e5→USER (~0.04)
на 24 вопросах неотличим от везения; на 76 — уже нет.

Что показали 76. Бейслайн и улучшенный почти равны:
  Hit@1  0.750 vs 0.737    Hit@3  0.855 vs 0.868
  nDCG   0.832 vs 0.803
Ранг эталонной страницы совпал на 69/76. Расхождения:
  бейслайн лучше на IDEF0 A-0, декомпозиции BPMN, журнале аудита,
  анализе ссылок;
  улучшенный — на удалённом бэкапе, физическом удалении, составе ССП.
Один полный промах улучшенного: «как понять, что BPMN декомпозирован»
(ушёл в visio/simulation). Старый «+0.02 nDCG от таблиц» на 24+авто
не воспроизвёлся — это и есть польза расширения набора.

Бейслайн заморожен (yaml + csv + коллекция). Улучшения рядом,
не вместо.

Дашборд: сетка чанкинга, эмбеддинги, retrieval, LLM, абляции,
сравнение со снимком бейслайна.

Слабое место оценки — сказать самим, не ждать вопроса:
итерации этапов A–E крутили на 24 вопросах; 76 собрали после.
Метрика всё ещё page-level. LLM-судья — та же семья моделей.

11. ЧТО ЕЩЁ МОЖНО УЛУЧШИТЬ И ЧЕГО ЭТО СТОИТ
══════════════════════════════════════════════════════════════════

Уже на плато по «очевидным» рычагам. Следующие шаги — либо
методология, либо задержка, либо лотерея модели.

A. Разбор ошибок по 24 ручным вопросам
   Стоимость: 1–2 часа.
   Эффект: понять, какие 6 из 24 не в Hit@1 — таблицы,
   семантика или неверная страница. Без этого новая модель —
   стрельба вслепую.

B. Расширить ручной goldset до 60–80 вопросов
   Стоимость: полдня разметки.
   Эффект: доверие к цифрам. Сейчас +0.02 nDCG ≈ 1 вопрос.

C. Новая эмбеддинг-модель (Qwen3-Embedding 0.6B / 4B)
   Стоимость: 1–3 часа скачать + индекс, 2–4 ГБ, полный bench.
   Эффект: 0…+0.04 nDCG, может быть минус. USER уже обошёл
   e5-large и bge-m3.

D. Более быстрый / мелкий реранкер
   Стоимость: вечер сравнения.
   Эффект: поиск 1.7 с → ~0.6–1.0 с. Риск −0.01…0.03 Hit@3.

E. Не генерировать ответ, пока не попросили
   Стоимость: 15 минут в UI.
   Эффект: 26 с ожидания → 2 с. Качество поиска то же,
   меняется UX. Для живого демо — самый дешёвый выигрыш.

F. 8 кандидатов вместо 16 у реранкера
   Стоимость: 20 минут бенча.
   Эффект: ~1 с вместо 1.7. Может отрезать Hit@3.

Не делать до презентации:
  дообучение на 24 примерах (переобучение),
  LLM-rewrite запроса (+2–4 с, риск сломать ловушки),
  агент / multi-hop,
  смена Qdrant.

12. СЛАБЫЕ МЕСТА (сказать самим)
══════════════════════════════════════════════════════════════════

1. Оценка. 76 ручных — уже не 24, но всё ещё page-level, не абзац.
   Синтетика (40) легче ручных и в «общий nDCG» этапов A–D ещё входит.
   Выбор чанкинга/эмбеддера крутили на старых 24.

2. Задержка ответа. 24 с — это продукт, не бенч поиска.
   Прогрев лечит только старт моделей.

3. LLM-судья. Обоснованность выставляет другая локальная модель,
   не человек. Цитата «1.0» не значит «идеальный ответ».

4. Совмещённые улучшения. nobc + expand + таблицы снимали
   поэтапно, не одним факториальным планом. Dual-index — лучшая
   точка, но вклад expand на nobc+tables отдельно не отделили.

5. Embedded Qdrant. Эксклюзивная блокировка каталога:
   UI и bench не живут вместе. Для демо ок, для продукта — сервер.

6. Streamlit. Это стенд, не портал справки.

7. Выборки. GitHub без полного корпуса. Воспроизведение —
   25 страниц, цифры в дашборде — с полного дампа.

8. Parent-document. В retrieval бесполезен (тот же embed).
   Для полноты ответа LLM не измеряли отдельно.


══════════════════════════════════════════════════════════════════
13. ВОПРОСЫ, КОТОРЫЕ ЗАДАДУТ — И КОРОТКИЕ ОТВЕТЫ
══════════════════════════════════════════════════════════════════

Q: Почему не FAISS / Elasticsearch / pgvector?
A: На 2500 чанках качество = эмбеддинг + реранкер, не ANN.
   Qdrant дал hybrid RRF без сервера.

Q: Почему не GPT-4 / облако?
A: Ограничение задания: on-premise, справка не уходит наружу.

Q: Почему 512, если 256 чуть лучше на ручных?
A: Тот же общий nDCG, вдвое меньше индекс. На USER потом
   всё равно 512.

Q: Почему Hit@1 только 0.75?
A: Page-level, 76 ручных. Один промах из четырёх на первом месте;
   Hit@3 0.87. Для справки «ответ в тройке» важнее. На 24 вопросах
   тот же Hit@1 прыгал на ±9 п.п. от одного примера.

Q: Улучшения же ухудшили nDCG?
A: На 76 ручных да, на 0.03. Hit@3 чуть выше. Ранги совпали на 69/76.
   Старый выигрыш таблиц измеряли на 24+авто — переоценили. Профили
   оставляем оба: бейслайн в UI, улучшенный по умолчанию.

Q: Реранкер 2 секунды — не слишком?
A: Да. Без него Hit@3 падает с ~0.92 до ~0.75 на e5.
   32 кандидата ещё медленнее и хуже по nDCG. Компромисс — 16.

Q: Вы учили fusion на goldset?
A: Нет. Пробовали эвристику, она проиграла. На 24 примерах
   учить веса нельзя.

Q: Откуда уверенность, что парсер правильный?
A: Тесты на живых конструкциях + инспектор. Без ::: вопрос
   про Ctrl+R не имеет ответа в индексе.
